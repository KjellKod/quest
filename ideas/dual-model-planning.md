# Dual-Model Planning

## Problem

Currently Quest generates one plan using a single model (the planner role). This means the planning phase only gets one perspective, and plan quality depends entirely on one model's strengths and blind spots.

## Idea

When two models are available (Claude + Codex), generate **two competing plans** in parallel during the planning phase:

1. **Plan A** -- generated by Model A (e.g., Claude)
2. **Plan B** -- generated by Model B (e.g., Codex)

Both plans address the same quest brief with the same constraints.

### Arbiter Selects the Best Plan

The arbiter (already part of the Quest pipeline) receives both plans and:

1. **Picks the winner** -- which plan is the primary plan going forward
2. **Extracts gold nuggets** from the losing plan -- specific ideas, edge cases, test strategies, or architectural insights that the winning plan missed
3. **Produces a merged plan** -- the winning plan enriched with the gold nuggets

This merged plan then enters the normal plan-review phase.

### When This Applies

- **Two models available:** Run dual planning (parallel, so no time penalty vs. sequential)
- **Single model only:** Skip -- run the current single-plan flow unchanged
- **Solo quest mode:** Skip -- solo quests use lightweight single-reviewer flow

### Flow

```
quest brief
    |
    +---> Model A planner ---> Plan A ---+
    |                                    |---> Arbiter ---> Merged Plan ---> plan-review
    +---> Model B planner ---> Plan B ---+
```

### Benefits

- **Diverse perspectives** -- different models have different strengths (system design vs. implementation detail, for example)
- **No time cost** -- both plans generate in parallel
- **Gold nugget extraction** -- even the "losing" plan contributes, so neither model's work is wasted
- **Natural fit** -- the arbiter role already exists and already evaluates plan quality

### Considerations

### Fail-Closed Multi-Model Requirement

The current allowlist can express a mixed-model intent, but Quest can still silently degrade to a single-runtime execution when one runtime is unavailable. That creates a truth gap: the repo appears configured for multi-model work, but the actual quest only used one model.

For operator-invoked Quest, add an explicit **require real multi-model execution** mode:

- If the allowlist or operator policy requires multiple models, Quest must verify that the distinct planned slots can actually run before starting the quest.
- If the required second runtime is unavailable, Quest should **exit the quest early** instead of silently continuing in single-model mode.
- Treat `preferred model` and `effective runtime/model` as different facts. Both should be recorded.

### What Must Be Persisted

For every role slot, Quest should persist at least:

- preferred model from policy/allowlist
- effective runtime used (`claude`, `codex`, etc.)
- effective model used
- whether fallback/degradation occurred
- why degradation happened when it did happen

### Why Memory Is Not Enough

This should not rely on agent memory or informal operator expectations. The hard requirement belongs in Quest's executable policy and runtime checks so that a future session cannot drift back into silent single-model execution.

- The arbiter prompt needs a new mode: "compare two plans" vs. "evaluate review feedback"
- Plan format must be identical so the arbiter can do apples-to-apples comparison
- Gold nugget extraction should be concise -- bullet points appended to the winning plan, not a full rewrite
- The merged plan should clearly mark which parts came from gold nugget extraction (traceability)

### Open Questions

- Should the quest brief include model-specific hints? (Probably not -- let each model interpret independently)
- Should the user see both plans before the arbiter picks? (Probably not by default -- but could offer a `--show-plans` flag)
- Does this change the plan iteration limit? (No -- the merged plan enters review as iteration 1, same as today)
